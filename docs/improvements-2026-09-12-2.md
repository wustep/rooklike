## Technical

### 1. A null or missing worker reply strands the battle forever
- **Impact:** 🔴 high · **Effort:** S · **Status:** ⬜ proposed
- **Problem.** `src/ai.worker.ts:2` posts `move?.san ?? null`; `src/App.tsx:61` does `if(e.data){...}` so a null reply is dropped and `thinking` stays true with no watchdog. `chooseMove` returns undefined when `assertPosition` throws or the root move list is empty. Only exit is a reload.
- **Proposal.** Handle `null` explicitly (notice plus resolve the position from the current `chess` state), add a watchdog timer that retries then recovers, assert the reply is a non-empty string before `playMove`.
- **Risks / trade-offs.** Watchdog on a slow device; make it retry-then-recover.
- **Files.** `src/App.tsx`, `src/ai.worker.ts`

### 2. Captain capture is scored as a flat WIN with no ply term
- **Impact:** 🔴 high · **Effort:** S · **Status:** ⬜ proposed
- **Problem.** `src/engine.ts:84` returns `WIN` for captain capture while checkmate uses `-WIN+ply` (`:80`) and the quiescence captain check uses `WIN-ply` (`:95`). Every losing line scores the same, so a doomed enemy cannot prefer delaying capture and dumps material ("enemy gave up" feel).
- **Proposal.** Return `WIN-ply` at `:84`; confirm the cached-score guard at `:113` still covers the range.
- **Risks / trade-offs.** Search ordering shifts; `tests/depth.test.ts` pins quality.
- **Files.** `src/engine.ts`

### 3. Every pointermove during a drag replays the game and rescans the board
- **Impact:** 🔴 high · **Effort:** M · **Status:** ⬜ proposed
- **Problem.** `App.tsx:52` calls `chess.history({verbose:true})` unmemoized; `:53` flattens the board per render; `:168-169` call `isAttacked`/`attackers` per square; `onDragMove` sets state on every pointermove; the keydown effect at `:117-127` has no dependency array.
- **Proposal.** Memoize `lastMove`/`checkedKing` on `[chess]`, precompute threatened/reach sets, coalesce drag moves with rAF, give the keydown effect deps.
- **Risks / trade-offs.** rAF batch must flush on pointerup.
- **Files.** `src/App.tsx`

### 4. The Hint Lens suggests a depth-1 move
- **Impact:** 🟡 med · **Effort:** M · **Status:** ⬜ proposed
- **Problem.** `App.tsx:116` calls `chooseMove(chess,'tactician',run.elite)` with `stage` defaulting to 0, so the hint uses the weakest profile and runs synchronously on the main thread.
- **Proposal.** Pass `run.stage` plus an override; route through the worker with a `kind:'hint'` message.
- **Risks / trade-offs.** Slower hint; cap nodes.
- **Files.** `src/App.tsx`, `src/ai.worker.ts`

### 5. `move()` banks a takeback entry before the move is known to succeed
- **Impact:** 🟡 med · **Effort:** S · **Status:** ⬜ proposed
- **Problem.** `App.tsx:74` calls `rememberTurn` before `playMove`; if `playMove` throws or returns `run` unchanged, a phantom history entry costs a Takeback for nothing. `setRun(next)` is a plain value, not an identity-guarded updater.
- **Proposal.** Compute `next` first, bail if unchanged, then push history and use the guarded updater; try/catch with notice.
- **Risks / trade-offs.** None material.
- **Files.** `src/App.tsx`

### 6. Recruit unit ids can collide after send-home
- **Impact:** 🟡 med · **Effort:** S · **Status:** ⬜ proposed
- **Problem.** `game.ts:168` builds ids as `recruit-${seed}-${stage}-${army.length}-${coins}`; `sendHome` can return the army to an earlier length with coins drifting back, so two units can share an id and `positions`/promotion retype the wrong unit.
- **Proposal.** Monotonic `nextUnitId` on `Run`, migrated in `loadRun`.
- **Risks / trade-offs.** Touches the `Run` shape.
- **Files.** `src/game.ts`

### 7. History heuristic mixes both colors
- **Impact:** 🟡 med · **Effort:** S · **Status:** ⬜ proposed
- **Problem.** `engine.ts:72` keys history moves by `from+to+promotion` without color, so ivory's good moves raise the ordering of the same black from-to pair.
- **Proposal.** Prefix the key with `m.color`.
- **Risks / trade-offs.** Ordering changes; depth tests guard.
- **Files.** `src/engine.ts`

### 8. Tests for en passant bookkeeping and the worker contract
- **Impact:** ⚪ low · **Effort:** S · **Status:** ⬜ proposed
- **Problem.** Claimed: nothing exercises en passant unit removal (`game.ts:138`) or the worker's `undefined → null` path. Orchestrator note: `tests/game.test.ts` already has "tracks white en passant and black en passant casualties"; only the worker-contract half stands.
- **Proposal.** A unit test of the `chooseMove → san|null` contract paired with idea 1.
- **Risks / trade-offs.** None.
- **Files.** `tests/game.test.ts`

### 18. Many armies physically cannot castle while the game teaches and pays for castling
- **Impact:** 🔴 high · **Effort:** M · **Status:** ⬜ proposed
- **Problem.** `makeBattle` (`game.ts:101-108`) deploys knights to b1/g1 and bishops to c1/f1, so two knights plus two bishops block both castlings from move one, while stage 6's lesson is "Castle before the files open" and the Hearthstone relic pays for the first castle.
- **Proposal.** Minimum: deployment order that keeps one side clear when a fallback square exists, plus a camp warning line. Full: deployment preview with same-rank swaps.
- **Risks / trade-offs.** Castling-rights derivation at `game.ts:111` and e2e deployment snapshots change.
- **Files.** `src/game.ts`, `src/App.tsx`

## DevEx

### 24. Worker accepts a search override, driven from a DEV-only test hook
- **Impact:** 🔴 high · **Effort:** S · **Status:** ⬜ proposed
- **Problem.** `src/ai.worker.ts:2` takes the `Run` as the whole message, so there is no channel for `chooseMove`'s existing `override`; with the 550ms think delay (`App.tsx:63`) the "complete act through the UI" spec runs 9-14 minutes at full strength.
- **Proposal.** Worker protocol `{run, override?}`; under `import.meta.env.DEV` read a Playwright-injected `window.__ROOKLIKE_TEST__` (or `?search=`) for a cheap profile and zero delay; drop the 900s timeout.
- **Risks / trade-offs.** The spec asserts ivory wins; weaken the enemy only, see 25.
- **Files.** `src/ai.worker.ts`, `src/App.tsx`, `e2e/game.spec.ts`
